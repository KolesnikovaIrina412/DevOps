# Правила внесения изменений

Документ описывает обязательный порядок работы с репозиторием: как вносить изменения, что проверять перед коммитом и как проходит приёмка.

## 1. Общие принципы

- **Ветка `main` защищена.** Прямые коммиты в `main` запрещены. Любое изменение проходит через отдельную ветку и Merge Request (MR) / Pull Request (PR).
- **Одна задача — одна ветка.** Ветка создаётся под конкретную задачу (issue, фичу, багфикс) и не смешивает несвязанные изменения.
- **Коммиты осмысленные.** Сообщение коммита должно объяснять, **что** и **зачем** сделано. Формат:

  ```
  <тип>: <краткое описание>

  <опционально — подробности>
  ```

  Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.

  Примеры:
  - `feat: добавлен healthcheck /health`
  - `fix: исправлена пагинация на второй странице`
  - `docs: обновлён README с описанием API`

## 2. Обязательные команды проверки перед коммитом

Перед каждым коммитом (и особенно перед MR) необходимо выполнить:

```bash
# 1. Убедиться, что PostgreSQL запущен
#    Windows: services.msc → postgresql-x64-16 → Running
#    Linux:   systemctl status postgresql

# 2. Убедиться, что переменные окружения заданы
cat .env
# Должны быть: SECRET_KEY, DATABASE_URL, AUTH_DATABASE_URL

# 3. Установить зависимости
pip install -r requirements.txt

# 4. Запустить приложение
python app.py

# 5. Проверить healthcheck
curl http://127.0.0.1:5000/health
```

Минимальный чек-лист:
- [ ] PostgreSQL запущен и доступен.
- [ ] `.env` содержит корректные `DATABASE_URL` и `AUTH_DATABASE_URL`.
- [ ] Приложение запускается без ошибок.
- [ ] `/health` возвращает `"status": "ok"`.
- [ ] Изменённый функционал проверен вручную (в браузере).
- [ ] Нет забытых `print()`, `TODO`, отладочного кода.
- [ ] Нет закомментированных блоков кода.
- [ ] `.env` **НЕ** попал в коммит (`git status` не показывает `.env`).
- [ ] `DATABASE_URL` в `.env.example` **не содержит реальных паролей**.

## 3. Запрещённые действия

| Действие | Почему запрещено |
| :--- | :--- |
| Прямой коммит в `main` | Нарушает процесс ревью, ломает историю |
| Коммит файла `.env` | Содержит секреты: `SECRET_KEY`, пароли PostgreSQL |
| Коммит реальных паролей в `.env.example` | `.env.example` — только плейсхолдеры |
| Коммит SQLite-БД (`*.db`) | Устаревшие, не должны попадать в репозиторий |
| Коммит `__pycache__/`, `.venv/` | Мусор, генерируется автоматически |
| Коммит больших бинарных файлов (> 10 МБ) | Засоряет репозиторий |
| `git push --force` в `main` | Уничтожает чужие изменения |
| Коммит с сообщением `fix`, `update`, `123` | Не несёт смысла |
| Смешивание несвязанных изменений в одной ветке | Затрудняет ревью и откат |
| Игнорирование замечаний ревьюера | Нарушает процесс приёмки |

## 4. Порядок внесения изменений

### Шаг 1. Создать задачу (issue)

Опишите проблему или задачу: что нужно сделать, зачем, критерии готовности.

### Шаг 2. Создать ветку от `main`

Именование веток:

```
feature/<краткое-описание>   — для новых фич
fix/<краткое-описание>       — для багфиксов
docs/<краткое-описание>      — для документации
refactor/<краткое-описание>  — для рефакторинга
```

Пример:

```bash
git checkout main
git pull origin main
git checkout -b feature/healthcheck-endpoint
```

### Шаг 3. Внести изменения

Делайте **несколько небольших коммитов** по ходу работы, а не один гигантский в конце. Каждый коммит — логически завершённый шаг.

```bash
git add config.py requirements.txt
git commit -m "feat: переход на PostgreSQL"

git add scripts/migrate_sqlite_to_pg.py
git commit -m "feat: скрипт миграции данных"
```

### Шаг 4. Запушить ветку

```bash
git push -u origin feature/postgresql-migration
```

### Шаг 5. Создать Merge Request

В GitHub/GitLab:
- Укажите **название** MR (соответствует задаче).
- В **описании** укажите: что сделано, как проверить, на что обратить внимание.
- Свяжите MR с задачей (issue).
- Назначьте **ревьюера**.

### Шаг 6. Пройти ревью

- Ревьюер проверяет код, оставляет комментарии.
- Автор вносит правки **в ту же ветку** (коммиты автоматически попадают в MR).
- После одобрения — **merge** в `main`.

### Шаг 7. Удалить ветку

После слияния ветку можно удалить:

```bash
git branch -d feature/postgresql-migration
git push origin --delete feature/postgresql-migration
```

## 5. Порядок приёмки

Изменение считается принятым, если выполнены **все** условия:

1. **Ветка создана от актуального `main`.**
2. **Все обязательные проверки пройдены** (см. раздел 2).
3. **MR создан** и связан с задачей.
4. **Ревьюер одобрил** изменения (как минимум один approve).
5. **CI/CD прошёл** (если настроен).
6. **Конфликтов с `main` нет** — ветка актуальна или ребейзнута.
7. **Коммиты осмысленные**, история читаемая.
8. **Документация обновлена** (если изменение затрагивает API, конфигурацию, схему данных).

Только после этого MR может быть слит в `main`.

## 6. Работа с версиями

- **Версия приложения** хранится в `app/version.py` (`__version__`).
- **Релизы** помечаются **аннотированными тегами**:

  ```bash
  git tag -a v0.1.0 -m "Первая версия: базовый функционал библиотеки"
  git push origin v0.1.0
  ```

- **Правила версионирования** — [Semantic Versioning](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH`.
  - `MAJOR` — несовместимые изменения.
  - `MINOR` — новая функциональность (обратно совместимая).
  - `PATCH` — багфиксы.
